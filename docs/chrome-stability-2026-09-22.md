# Chrome 稳定性排查（2026-09-22）

用户报告：更新后多次电脑蓝屏，操作集中在合并数据、上下滚动页面、切换线条显示。

已复现浏览器渲染开销问题并作针对性修复，但没有复现系统蓝屏，也没有取得停止代码或系统转储。下列结果不能证明蓝屏根因已经解决。

`git blame` 显示逐标签 `getBBox()` 和卡片背景模糊早于本次更新。不能将这些问题全部归因于最近两天的提交。最近更新未引入 WebGL 或新的运行时依赖。

## 修复与测量

环境为 Linux、headless Chromium `153.0.8010.12`、1440 × 1000 viewport，通过本地 Vite 开发服务运行。API 请求使用拦截或离线数据，避免网络变化影响结果。这不是用户的 Windows/Chrome/显卡驱动环境。

性能用例使用 5 条曲线，每条 100 个点，交替设置 Prefill DCP 8/16，Decode DCP 1，展开数据表并启用 Gradient Labels。合并其中 4 条后，上下滚动，再切换剩余独立曲线 10 次：

| 指标 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 10 次切换期间 `LayoutCount` 增量 | 1,530 | 40 |
| 10 次同步切换耗时（单次测量） | 255 ms | 185 ms |
| 滚动后有内容的合成图层数 | 564 | 558 |

- **标签布局**：先批量写入文本，再批量读取尺寸，最后更新背景框，消除每个标签读写交错导致的强制布局。验证了背景框尺寸与文本一致。
- **背景模糊**：导航栏、浮动工具栏和卡片改为不透明背景，移除 `backdrop-filter`。这是减少合成工作的措施；图层数仅小幅下降，不能据此断定 GPU 驱动问题或蓝屏已解决。
- **主题切换**：保留数据表 DOM、输入内容和事件处理器，只更新颜色；主题仍由独立的存储项持久化。隐藏工作区在重新进入时更新颜色。

另外，在 500 点的未合并数据上切换主题 12 次，平均同步处理时间由约 368 ms 降到 164 ms，数据表不再重建。重复主题和工作区切换后，回收后的 JS heap 约为 6–8 MiB，没有观察到持续的大幅增长；这不包含浏览器原生内存或 GPU 显存。

## 验证

- `npm run build`、`npm run check:dcp`、`npm run check:model-tco`、`git diff --check` 通过。
- 合并后 500 个点保留完整，CSV 导出包含全部 500 行数据。
- 浏览器检查覆盖 DCP 标签/颜色/tooltip、真实缓存 Kimi K3 快照、图例显示切换、数据编辑、CSV 导入导出与持久化。
- 默认筛选、主题切换时的编辑精度与焦点、工作区切换、折叠状态、PNG 导出和窄屏布局通过。
- Throughput 与 TCO 视图的全量/可见 CSV 均符合 `docs/import-csv.md`，继续导出原始吞吐量。

测试未触发页面异常或浏览器崩溃。仍需用户环境的蓝屏停止代码及必要时的 minidump，才能判断是否涉及显卡驱动、其他内核驱动或硬件。在确认前，可先到 `chrome://settings/system` 关闭图形加速并重启 Chrome，作为临时规避和诊断对照；不要反复执行已经导致蓝屏的压力操作。
